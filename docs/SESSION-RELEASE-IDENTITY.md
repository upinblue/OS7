# The release identity — a version number, and where it shows up

[RELEASE-AND-UPDATE-PLAN.md](RELEASE-AND-UPDATE-PLAN.md) §10 Phase 1:

> `build/config/os7-release.conf` as the single pin file; build emits
> `/usr/lib/os7/release.json` and the selections manifest; os-release branding
> per §3.5; version threaded into the ISO name and BE name.

**Date:** 2026-08-24.

This phase was pulled forward, ahead of SETUP-PLAN Phase 3. The reason is worth
stating because it is not scheduling preference:

> **There was no version number anywhere in the repository.**
> `/usr/lib/os7/release.json` was specified and generated by nothing.
> `/etc/os-release` was unbranded. `New-OS7BootEnvironmentName` looked for the
> manifest, never found it, and fell back to `0.0.0.0`. The GRUB menu read
> "Ubuntu 26.04 LTS".

Phase 3 configures the installed system, and three of the things it must write
there are the version: `/etc/os-release` (D8), the GRUB menu title (L4) and the
boot-environment name (§4.4). Phase 3 could not have been done correctly first.

The immediate prompt was a product request — *show the OS/7 version in Setup* —
which turned out not to be a UI task at all.

## What exists now

| | |
|---|---|
| **The pin** | [`build/config/os7-release.conf`](../build/config/os7-release.conf) — version fields, channel, archive snapshot, every component version and hash. **The only place in the repo that may carry a version number or an archive URL.** |
| **The archive** | Every build resolves against `snapshot.ubuntu.com/ubuntu/20260824T000000Z/`. Fourteen mirror flags, both families. |
| **The manifest** | [`build/config/hooks/0075-release-identity.hook.chroot`](../build/config/hooks/0075-release-identity.hook.chroot) writes `/usr/lib/os7/release.json` and `/usr/lib/os7/packages.manifest`, and brands `/usr/lib/os-release`. |

## The four decisions, and their consequences

**`1.0.0.0`, not `0.1.0.0`.** §3.3 defines MAJOR as the Ubuntu LTS generation —
`1.x` = 26.04. Using it to signal maturity would break the one rule the field
has. Maturity is `OS7_CHANNEL`, which reads `development` and is printed in
brackets after the number on every screen until it does not.

**BUILD is `git rev-list --count HEAD`.** §3.3 calls this "the CI build number"
and there is no CI here by design. A hand-maintained counter was the alternative
and is worse: two builds could carry one number and different bits, which is
exactly what §3.1 forbids. The commit count is monotonic on a linear main, needs
no state file, and can be recomputed from the repository years later.

Its two honest limits are recorded rather than hidden. A build from a branch is
not comparable with one from main. And a **dirty tree** means the number does not
identify the source — so `reproducible: false` goes in the manifest, the build
says so on stdout, and the Welcome screen prints *"This build was not made from
a clean source tree."* A warning that scrolls past is not a warning; the ISO
outlives the terminal it was built in.

**The whole pin, including the archive.** The alternative — ship the identity
now, pin the archive later — would have been cheaper and would have left the
number naming a build rather than a state, which §3.1 argues is worse than
having no number.

**TPM2 enrolment moves into Phase 3**, and Phase 3's chroot steps take the target
root as a parameter. Both are recorded in SETUP-PLAN §10; neither is done yet.

## What was measured

### The snapshot service, before pinning anything to it

Checked live on 2026-08-24. `snapshot.ubuntu.com` was verified in the release
plan on 2026-08-23; this is re-verification against the timestamp actually being
pinned, because "it worked last week for a different stamp" is not the claim.

| Check | Result |
|---|---|
| `…/ubuntu/20260824T000000Z/dists/resolute/Release` | `200`, `Date: Thu, 23 Apr 2026 17:07:15 UTC` — the frozen release suite |
| `…/dists/resolute-updates/Release` | `200`, `Date: Sun, 23 Aug 2026 23:58:59 UTC` |
| `…/dists/resolute-security/Release` | `200`, `Date: Sun, 23 Aug 2026 23:58:45 UTC` |
| `…/dists/resolute/main/binary-arm64/Packages.gz` | `200`, 1 860 484 bytes |
| `…/dists/resolute/main/binary-amd64/Packages.gz` | `200` |

So the stamp resolves to an **instant**, not a rounded day: the archive as it
stood just before midnight on 2026-08-23. And **arm64 is served under the same
`/ubuntu/` path as amd64** — the `archive`/`ports` split does not exist here, so
pinning *removed* the per-architecture branch `auto/config` used to carry.

### The mirror leak — BUILD-NOTES #36

`auto/config` was written with the five obvious flags. Reading `config/bootstrap`
back after `lb config` — thirty seconds, no build — showed two that were not:

```
LB_MIRROR_CHROOT_VOLATILE="http://archive.ubuntu.com/ubuntu/"
LB_MIRROR_BINARY_VOLATILE="http://archive.ubuntu.com/ubuntu/"
```

**"Volatile" is Debian's name for what Ubuntu calls `-updates`.** The two flags
nobody thinks to set are the ones covering the suite that *moves*. A build like
that draws its base from a fixed snapshot and its updates from the live archive,
and is unreproducible while every flag on screen says it is pinned.

After setting all fourteen, nothing outside the snapshot remains except
`*_BACKPORTS="none"`, which is disabled rather than defaulted.

One claim checked before making it: the pre-pin ISO's
`deb http://security.ubuntu.com/ubuntu/ resolute-security` on **arm64** looked
like a second bug, since ports architectures normally live on
`ports.ubuntu.com`. It is not — `security.ubuntu.com` serves `binary-arm64` with
a `200`. It was a reproducibility hole, not a broken source.

### The manifest has to carry versions — BUILD-NOTES #37

§3.4 specifies `dpkg --get-selections` for `packages_manifest`, and §5 wants that
hash to catch an admin running `apt upgrade` behind the release train's back.

**It cannot.** Selections record package *names* and an install state, so a
system holding `linux-image 7.0.0-28` and one holding `7.0.0-31` produce
byte-identical output. The hash matches; the drift is invisible.

Hook 0075 writes `package<TAB>version<TAB>architecture`, sorted. A strict
superset, and it makes both things the manifest exists for actually work — drift
detection (§5) and comparing two builds of one release (S7). Without this, S7
would have passed while testing nothing.

### `/etc/os-release` — BUILD-NOTES #37

It is a symlink to `../usr/lib/os-release`, which `base-files` owns as a
**conffile**. So the branding is written to the real file, and it has to be
re-asserted after any `apt` run — which is why §4.2 step 6 exists.

Read back by **sourcing** it, never scraping it. The first version of the hook's
own readback stripped only double quotes while its writer emitted single ones —
a check that would have failed a correct file.

Also, §3.5's example shows `ID_LIKE=ubuntu`; the real file says
`ID_LIKE=debian`. It does not matter, since that is one of the three fields left
alone for Intune, but do not "fix" the file to match the example.

### A measurement that did not survive the build — BUILD-NOTES #38

Worth recording in full, because the mistake is instructive and the design
decision that absorbed it is the reusable part.

Hook 0075 wants to prove the chain end to end by asking the OS7 module for a boot
environment name — which calls `Test-Path`, `Get-Content`, `ConvertFrom-Json`.
BUILD-NOTES #14 appears to say that cannot work at build time, so it was measured
rather than assumed: overlay the shipped squashfs, bind `/dev` and `/proc`,
chroot, ask.

```
os7_1.0.0.32_202608241502
```

It worked, and the conclusion drawn — *bundled cmdlets resolve under
`chroot(2)`* — **was wrong.** The first ISO build printed:

```
OS/7 hook 0060:   manifest loads, exports: New-OS7BootEnvironmentName, New-OS7Storage, …
OS/7 hook 0075:   NOTE: … included, verify that the path is correct and try again.
```

Same build, twenty lines apart. The module **imports** by path and its functions
are **listed**; *calling* one fails, and that second sentence is PowerShell's
command-not-found message. So the line is not import-by-path versus
import-by-name — it is **anything that has to be autoloaded by name out of
`$PSHOME/Modules`**. Hook 0060 uses only `Get-Command` (compiled into the engine)
and `[Console]::WriteLine` (pure .NET) and has always stayed on the right side of
it. Why the overlay chroot disagreed is not isolated, and that is stated rather
than guessed at.

**The reusable part is the design decision, not the measurement.** Hook 0075
treats *"PowerShell produced no answer"* as a NOTE and *"PowerShell produced the
WRONG version"* as fatal. Written the obvious way — assert the name, fail
otherwise — this build would have stopped on a perfectly good image. Separating
**cannot tell** from **wrong** is what made a wrong belief cost nothing.

Which is the same lesson as the diagnostic rule already in
[BUILD-NOTES.md](BUILD-NOTES.md), arrived at from the other direction: a check
that cannot distinguish absence of evidence from evidence of absence will
eventually report the first as the second.

## Where the version is checked

Four places, deliberately at four different distances from the thing itself.

| Where | What it proves | Fails when |
|---|---|---|
| Hook 0075, in the chroot | os-release was branded and the Intune-matched fields were not touched; the manifest parses; the module reads it | the ISO build stops |
| `os7-setup --self-test`, hook 0080 | the manifest is present, has a version that is not `0.0.0.0`, and names an archive snapshot; the title row holds the stamp at 80 columns and drops it at 28 | the ISO build stops |
| `check-image.py`, on the artefact | the FINISHED image — its `sources.list`, its os-release, its volume label, and `os7-setup --version` run by chrooting into it | seconds, no VM |
| `run-phase1.py`, in a VM | the version is **on the screen**, read back through the console font and compared with the manifest that shipped in the ISO | a screen shows the wrong number, or none |
| `run-phase2.py`, in a VM | **the boot environment on the disk is named after it**, and — in the new `existing` phase — that a second boot can read that version back OFF the disk | the module did not read the manifest |

The last two are the load-bearing checks, and they are the only ones that are
statements about a real disk. Everything before them verifies a step.

`check-image.py` exists because the build cannot check itself from inside. Two of
its checks are things hook 0075 structurally cannot see, and both found a real
problem the first time they ran:

* **the shipped `/etc/apt/sources.list`.** The hook runs mid-build, before
  live-build rewrites apt for the binary stage. This is where BUILD-NOTES #36
  would show up if it ever regressed — and it now reads
  *"every apt source in the image is pinned — all on snapshot.ubuntu.com"*.
* **the ISO volume label**, which is on the medium and not in it. It read
  `OS7-arm64` when `lb config` had been told `OS7-1.0.0.32-arm64` — see below.

None of these carries an expected version as a string. Hook 0075 reads the pin,
`--self-test` reads the manifest, `check-image.py` compares the image against
itself, and both harnesses take the number out of the image. A harness that
carries the number passes until somebody forgets to edit it.

### `--iso-volume` does nothing on arm64 — BUILD-NOTES #40

Found by reading the label off the finished ISO, which is the only way it could
have been found. `lb config` recorded `LB_ISO_VOLUME="OS7-1.0.0.32-arm64"`
faithfully; the ISO said `OS7-arm64`.

`build/lib/arm64-efi-remaster.sh` does not modify live-build's ISO — it builds a
**new one** with `xorriso`, because live-build emits no arm64 bootloader at all.
So every ISO9660 property live-build was configured with is discarded at the last
step, and a hardcoded `-volid` quietly won.

The nastiest part is that it is architecture-dependent: amd64 keeps live-build's
ISO, so there the same flag works. One setting, two behaviours, visible only on
the artefact. The volume id now comes from the output filename the caller already
passes, so the label on the medium and the name of the file cannot disagree.

### One of my own diagnostics was wrong in the same way

`check-image.py`'s first version ran `cd /mnt/sq && ./usr/lib/os7-setup/os7-setup
--version` and reported *"no release manifest on this medium"* about an image
that had one — because the binary resolves `/usr/lib/os7/release.json` against
the real root, so it read the build container's filesystem. It now overlays the
squashfs and chroots, the spike S2 pattern. Recorded because it is the third time
in this session that a check did not check the thing it claimed to.

None of these carries an expected version as a string. Hook 0075 reads the pin,
`--self-test` reads the manifest, and both harnesses take it out of the image.
A harness that carries the number passes until somebody forgets to edit it.

## The version, on the screen

`run-phase1.py all` — four phases, all PASS. Each screen is read back through the
console font the image ships, so this is a statement about the characters on a
framebuffer, not about what the code intended to draw:

```
      ok    title row carries 'Version 1.0.0.32 (development)'
      ok    screen 1 names the release
      ok    screen 1 names the archive snapshot it was built from
```

The expected string is not written into the harness. `title_stamp()` composes it
from the manifest the ISO shipped, applying the same rule `Model/Release.cs`
applies — bare number on `stable`, channel in brackets otherwise. So the check
fails if hook 0075 wrote a different number, if Setup read the wrong file, and if
the rule about channels ever diverges between the two.

## Reading the version off an installed disk

Screen 4 now says "OS/7 installation" instead of "GPT, 3 partitions", names the
version, and asks twice before erasing it. The mechanism is worth recording
because it constrains the upgrade path:

* **Recognising the layout is free.** `os7-esp`, `os7-bpool`, `os7-luks` are GPT
  partition names `PartitionStep` writes, and `PARTLABEL` is one more column on
  an `lsblk` call screen 4 already makes.
* **The version needs an import**, so it runs only for the selected disk.
* **`bpool` is unencrypted** (§4.2, D3, because GRUB must read it) and the boot
  environment names in it carry the release. So **the version of an installed
  OS/7 is readable without the passphrase** — the release manifest itself is on
  `rpool`, behind LUKS, and would not be.

The import is `-o readonly=on -N -f -R <altroot> -d <partition>`, exported in a
`finally`. `readonly=on` is what makes `-f` harmless; `-N` means there is nothing
mounted for the export to trip over (BUILD-NOTES #18).

**Verified against a disk this installer made**, by a phase written for it:
`run-phase2.py existing`. Every other phase in that harness starts from a blank
disk — `lab.prepare()` recreates the qcow2 — so none of them ever met the case a
real machine is usually in. This one installs OS/7 unattended, exports the pools,
reboots, and runs Setup against that same disk:

```
      ok    fixture: a disk carrying OS/7 1.0.0.32
      ok    the list marks the disk as carrying OS/7
      ok    screen 4 names the installed version (1.0.0.32)
      ok    erasing it needs a second ENTER
      ok    a second ENTER continues to screen 5
```

Which makes it **the only round trip the version number gets**: written into a
dataset name by one boot, read back off the disk by a different mechanism in the
next. The screendump is `.vm/phase2/shots/31-existing-named.png`:

> `vdb already carries OS/7 1.0.0.32. Press ENTER again to erase it.`

One detail worth keeping: the wait for the probe is a **poll with a deadline**,
not a sleep. Importing and exporting a pool is seconds rather than frames, and
how many seconds depends on the VM — a fixed sleep would decide between a flaky
harness and a slow one, and its failure would read as *"Setup did not detect the
installation"*, which is a wrong answer rather than a slow one. On timeout it
prints every brand-coloured row it did find.

## S7 — the version number is true

```
S7 PASS: two builds from 20260824T000000Z hold
         identical package sets — 549 packages, manifest sha256 ffd05e12c9cb3d08…
         1.0.0.32 names a state, not a moment.
```

Two full `make build-arm64` runs from the same pin and the same commit, compared
by their package manifests. **549 packages, the same versions, the same hash.**

That is the spike RELEASE-AND-UPDATE-PLAN §10 makes the whole version scheme
conditional on: *"If not, the pinning model is incomplete and §3 needs revisiting
before anything is shipped."* It does not need revisiting.

Two honest limits on what it proves:

* **Not bit-identical ISOs**, and it was never that claim. squashfs records
  timestamps and the manifest carries a build time. The claim is the narrower one
  the version number actually rests on: the same pin gives the same software.
* **Both builds came from a dirty tree**, so `reproducible: false` in both. The
  *Ubuntu* half of the comparison is what the pin covers and is unaffected; the
  OS/7 half is pinned by nothing until the tree is committed. `run-s7.py` says so
  rather than quietly comparing anyway.

The finished image was then asked what it is, without booting it:

```
The image is OS/7 1.0.0.32 (development), arm64, built 2026-08-24T16:13:27Z
from archive snapshot 20260824T000000Z, and every source in it says so.
```

Including `os7-setup --self-test` run by chrooting into the image:
`SELFTEST-DONE failures=0 image-files-absent=0`.

## What this does not do
* **amd64 remains unbuilt**, so everything here is arm64-only — as is everything
  else in this repository.
* **`Get-OS7Version` does not exist.** The manifest is written and read; the
  cmdlet surface in §6 that would report it, and the drift detection in §5 the
  manifest now makes possible, are Phase 3 of the release plan.
* **Nothing writes the identity onto an installed system yet.** Hook 0075 brands
  the image. The target gets it in SETUP-PLAN Phase 3, along with the GRUB menu
  title that still reads "Ubuntu 26.04 LTS".
* **The pin has a cost nobody had measured:** `snapshot.ubuntu.com` is
  noticeably slower than `ports.ubuntu.com` for a cold debootstrap. It is a
  build-time cost only, and it buys the one property the version number rests on.
